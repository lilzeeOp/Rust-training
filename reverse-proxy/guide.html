Reverse Proxy in Rust

A complete guide from TCP sockets to HTTP/2 — written for software engineers who are learning this for the first time.

This page walks through four real implementations, built in order from simplest to most production-ready. Every code snippet is taken directly from the source files.

1. Background Concepts

Before we talk about reverse proxies, we need to make sure the foundations are solid. This section explains the five concepts that everything else builds on.

What is a server and a client?

A server is a program that waits. It opens a port, sits there, and accepts connections from anyone who calls. A client is a program that initiates. It reaches out to a server at a known address and says "I want to talk."

The simplest mental model: think of a server as a phone operator sitting at a desk with headphones on. The client is anyone who dials in. The operator never calls you — you always call them.

The "address" of a server is two things combined: an IP address (which machine) and a port number (which program on that machine). For example, 127.0.0.1:8080 means "my own machine, port 8080." The operating system routes incoming connections to the right program based on the port.

What is a TCP connection?

TCP is a pipe. When a client and server establish a TCP connection, they get a reliable, ordered, bidirectional stream of bytes. You can think of it as two garden hoses duct-taped together — bytes go in one end and come out the other end, in the same order, without gaps.

Before data flows, there is a "three-way handshake": the client sends SYN ("I want to connect"), the server replies SYN-ACK ("I accept"), the client replies ACK ("great"). After that, both sides can read and write freely. When they are done, either side can close the connection.

The important thing to understand: TCP knows nothing about HTTP, or JSON, or images, or anything with meaning. It only knows bytes. Any meaning is layered on top by higher-level protocols.

What is HTTP?

HTTP (HyperText Transfer Protocol) is a text-based protocol that runs over TCP. It defines a request/response format — the client sends a request, the server sends a response, that's one round trip.

Here is what an actual HTTP request looks like as raw bytes on the wire:

GET /index.html HTTP/1.1\r\n
Host: example.com\r\n
Accept: text/html\r\n
\r\n

Breaking that down:

  • Line 1 — the request line: method (GET), path (/index.html), version (HTTP/1.1).
  • Lines 2–3 — headers: each is a key-value pair separated by a colon.
  • The blank line — a bare \r\n\r\n (carriage-return + newline, twice) signals the end of headers. The server stops reading headers here.
  • After the blank line, an optional body can follow (for POST requests, file uploads, etc).

The server reads that, processes it, and sends back a response:

HTTP/1.1 200 OK\r\n
Content-Type: text/html\r\n
Content-Length: 13\r\n
\r\n
Hello, World!

The response has a status line (version, code, reason), headers, a blank line, and then the body. The status code tells you what happened: 200 = success, 404 = not found, 502 = bad gateway, 503 = service unavailable.

That is the entire protocol at its core. HTTP/1.1 is literally this text format going back and forth over a TCP connection.

What is HTTPS and TLS?

The problem with plain HTTP is that anyone who can see your network traffic (your ISP, someone on the same Wi-Fi, a compromised router) can read every request and response. Passwords, tokens, session cookies — all visible.

TLS (Transport Layer Security) solves this by encrypting the bytes before they go on the wire. HTTPS is just HTTP running over a TLS-encrypted TCP connection instead of a plain TCP connection.

When a TLS connection starts, there is a handshake before any application data flows:

  1. Client Hello — the client says hello, lists the cipher suites it supports (the encryption algorithms it knows), and picks a random number for key generation.
  2. Server Hello + Certificate — the server picks a cipher suite, sends its certificate (a file containing the server's public key plus a digital signature from a trusted authority proving who the server is), and contributes its own random number.
  3. Key exchange — both sides use the random numbers and the certificate's public key to derive a shared secret. This uses math (Diffie-Hellman or similar) where each side can compute the same number without ever sending that number over the wire.
  4. Finished — both sides confirm with a small encrypted message to prove they derived the same keys.

After the handshake, all further bytes are encrypted with those shared keys. An observer can see that a connection happened and roughly how much data moved, but not the content.

A self-signed certificate is a certificate where you signed it yourself instead of having a trusted authority (like Let's Encrypt) sign it. Browsers will warn users about self-signed certs because the browser cannot verify who made them. But for development and internal tools, they are completely fine — the encryption still works, you just need to tell your HTTP client to accept the cert without verifying the signature (the -k flag in curl).

What is HTTP/2 and why does it exist?

HTTP/1.1 has a performance problem called head-of-line blocking. In HTTP/1.1, a single connection can only have one in-flight request at a time. If you want to load a web page that references 20 CSS files, 15 JavaScript files, and 40 images, your browser has to either make 75 sequential requests on one connection, or open many connections (browsers typically open 6 per domain). Both approaches are wasteful.

HTTP/2 solves this with multiplexing: many requests can be in flight simultaneously over a single connection. It does this by breaking messages into numbered frames and labeling each frame with a stream ID. The server can receive frames from stream 1, 4, 7 all at once, process them concurrently, and send back frames for each — interleaved however the network allows.

HTTP/1.1 — one at a time:
[Request 1] → [Response 1] → [Request 2] → [Response 2]

HTTP/2 — multiplexed:
[Req 1 frame] [Req 2 frame] [Req 3 frame]
          ↓         ↓         ↓
[Resp 1 frame] [Resp 3 frame] [Resp 2 frame]  (any order)

HTTP/2 also compresses headers using a scheme called HPACK, which avoids sending the same headers (like Accept-Encoding, Cookie) over and over.

HTTP/2 requires TLS in practice (browsers only implement HTTP/2 over encrypted connections). This means the client and server need to agree on which protocol to use during the TLS handshake itself. They do this with an extension called ALPN (Application-Layer Protocol Negotiation).

During the TLS handshake, the client includes a list of protocols it supports, like ["h2", "http/1.1"]. The server picks the best one it also supports and tells the client. By the time the handshake finishes, both sides already know if they are speaking HTTP/2 or HTTP/1.1 — no extra round trip needed.

What is async/await in Rust?

Imagine a web server that handles connections by assigning one OS thread per connection. Threads are fairly expensive — each one costs several megabytes of memory for its stack. If you have 10,000 simultaneous connections, you need 10,000 threads, which costs tens of gigabytes of RAM just for stacks. That is the "C10K problem" — how do you handle 10,000 concurrent connections without 10,000 threads?

The answer is async I/O. Instead of having the thread sit idle waiting for data to arrive on a socket, you register that socket with the operating system's event system (called epoll on Linux, kqueue on macOS, IOCP on Windows). When data arrives, the OS notifies you, and you process it. One thread can manage thousands of sockets this way.

In Rust, this is expressed through the async/await syntax. When you write:

let data = stream.read(&mut buf).await;

The .await means: "start this read operation, but if no data is available yet, yield control back to the runtime so other tasks can run. Resume me when data is ready." The function does not block the thread — it pauses itself and lets something else run.

The thing that gets paused is called a Future. A Future is a value that represents an operation that has not completed yet. When you call .await, you hand that Future to the runtime and say "run me when this is done."

Tokio is the runtime that makes this work. Tokio starts a thread pool (typically one thread per CPU core), and distributes Futures across those threads. When a Future is waiting for I/O, Tokio parks it. When the OS signals that the I/O is ready, Tokio wakes it up and puts it back on a thread to continue running.

When you call tokio::spawn(async move { ... }), you are creating a new task — a lightweight unit of work scheduled by Tokio. Tasks are much cheaper than OS threads. You can have hundreds of thousands of tasks on a handful of threads.

How does this compare to Go goroutines? Underneath, Go goroutines and Rust async tasks use the same OS primitives (epoll on Linux). Go goroutines are stackful coroutines — each goroutine gets a small growable stack. Rust Futures are stackless — they store only the state they need in a generated state machine struct. Rust Futures have no runtime overhead at all when not awaited. The tradeoff: Go's model is simpler to write, Rust's model is more explicit about what runs and when.

2. What is a Reverse Proxy?

Forward proxy vs. reverse proxy

A forward proxy sits in front of clients. Clients route their outbound traffic through it. The proxy makes requests on behalf of the clients. Companies use forward proxies to control what websites employees can visit, to cache content, or to anonymize traffic. The server being talked to may not even know a proxy is involved.

A reverse proxy sits in front of servers. Clients talk to the proxy, thinking it is the final server. The proxy forwards requests to the real server(s) behind it, and streams the response back. The client may not know (or care) that a proxy is involved.

Forward Proxy Reverse Proxy
Sits in front of Clients Servers
Who configures it The client (or client's org) The server operator
Client knows about it Usually yes Usually no
Common use Content filtering, caching, VPN-like Load balancing, TLS termination, routing

The receptionist analogy

Imagine you walk into a large company's lobby and say "I need to speak to someone about my account." The receptionist takes your request, figures out which department handles accounts, routes you to that person, and comes back with an answer. You never went directly to the account manager. You don't know their extension, which floor they are on, or whether they were out sick and someone else handled your request. The receptionist is the reverse proxy.

This is exactly what happens with a reverse proxy in production:

  • Your browser sends a request to api.example.com.
  • DNS resolves to the reverse proxy's IP address.
  • The proxy receives the request, picks one of three backend servers, forwards the request.
  • The backend responds. The proxy streams that response back to your browser.
  • Your browser never knew there were three servers behind that one address.

Why companies use reverse proxies

  • Load balancing — spread requests across multiple backend instances so no single server gets overwhelmed. If one backend crashes, the proxy stops sending it traffic.
  • TLS termination — decrypt HTTPS once at the proxy, forward plain HTTP to backends on the internal network. Backends stay simple and don't need TLS configuration. The internal network is trusted.
  • Health checking — the proxy periodically checks if backends are alive. Dead backends are automatically removed from rotation. Clients never see failures from a dead backend.
  • Hiding backend topology — backends can be on internal IPs, any port, any number of machines. The outside world only sees one address. You can add, remove, and replace backends without any client configuration changes.
  • Observability — inject headers like X-Request-ID to trace a request through logs across multiple services. Log every request with timing. Add X-Forwarded-For so backends see the real client IP even though the TCP connection came from the proxy.

3. The Four Options — Why We Built Them in This Order

Each option adds exactly one real production concern. The progression is not arbitrary — it mirrors how you would actually build a proxy in real life: start with the simplest possible thing that works, then add what you need when you need it.

The design principle Do not add complexity until you understand why you need it. Each option here breaks in a specific, concrete way. Understanding those limitations is more valuable than having a feature-complete proxy you don't understand.

A TCP Passthrough Forward raw bytes between client and one upstream Async TCP, tokio::spawn, bidirectional copy Load balance, read HTTP, HTTPS, add headers
B HTTP/1.1 Load Balancer Parse HTTP headers, rewrite them, round-robin across 3 upstreams httparse, header injection, AtomicUsize counter TLS, health checking, HTTP/2

4. Option A — TCP Passthrough

A

File: a-tcp-passthrough/src/main.rs and src/proxy.rs

This is the simplest possible proxy. It does not know anything about HTTP. It does not read, parse, or modify the bytes in any way. It just opens a connection to one fixed upstream and copies bytes in both directions.

Key concepts in main.rs

TcpListener::bind

Binding to a port is how you tell the OS "I am the program that owns port 8080 on this machine." The OS will start delivering incoming TCP connections to you. If another program already has that port, bind fails. If you try to bind to a port below 1024 on Linux/macOS, you need root privileges.

let listener = tokio::net::TcpListener::bind(config.listen_socket_addr()).await?;

The .await here just means "wait for the OS to confirm the bind succeeded" — this is fast and nearly synchronous, but everything in async Rust needs to be awaited.

The accept loop

listener.accept() waits for the next client to connect. It returns the socket for that new connection and the client's address. This call yields — while waiting for a client, the Tokio runtime can run other tasks. When a client connects, this call resolves.

Notice the tokio::select! macro. It runs two futures simultaneously and takes whichever one resolves first:

  • Branch 1: a new connection arrived
  • Branch 2: CTRL+C was pressed

This is how graceful shutdown works — when you press CTRL+C, the loop exits, no more connections are accepted, and existing tasks run to completion.

tokio::spawn

Each connection is handled in its own task via tokio::spawn(async move { ... }). Without spawn, the accept loop would block while handling the first client, and the second client would wait. With spawn, each client gets its own task that runs concurrently. Tokio schedules all tasks across a thread pool.

The move keyword means the closure takes ownership of the variables it uses (client, config, active). This is Rust's way of saying "this task owns its data, no sharing problems."

tokio::io::copy_bidirectional

This function does the actual work: it reads bytes from client and writes them to upstream, and simultaneously reads bytes from upstream and writes them to client. It does this concurrently — it does not wait for one direction to finish before starting the other. It returns when either side closes the connection.

Because this is pure byte copying, it works for any protocol — HTTP, HTTPS, WebSockets, custom binary protocols. It doesn't care what the bytes mean.

AtomicUsize for the active connection counter

We want to count active connections and print it in the log. The counter is shared across many tasks. We could use a Mutex<usize>, but that would require locking and unlocking. Instead, we use AtomicUsize — an integer that can be incremented and decremented safely from multiple threads at the same time without any locking. The CPU provides hardware instructions for this. Atomics are the right tool when you just need a counter.

The full source code

//! Level 3 — Production grade TCP passthrough.
//!
//! Adds: connect/transfer timeouts, graceful CTRL+C shutdown,
//! active connection counter, structured logging with env-filter.

mod config;
mod proxy;

use std::sync::{
    atomic::{AtomicUsize, Ordering},
    Arc,
};

use anyhow::{Context, Result};
use tracing::{error, info};

/// Resolves when CTRL+C is received.
async fn shutdown_signal() {
    tokio::signal::ctrl_c()
        .await
        .expect("failed to install CTRL+C signal handler");
}

#[tokio::main]
async fn main() -> Result<()> {
    // env-filter reads RUST_LOG at startup.
    // Example: RUST_LOG=a_tcp_passthrough=debug cargo run
    tracing_subscriber::fmt()
        .with_env_filter(
            tracing_subscriber::EnvFilter::from_default_env()
                .add_directive("a_tcp_passthrough=info".parse().unwrap()),
        )
        .init();

    let config = Arc::new(
        config::Config::load("config.toml").context("failed to load config.toml")?,
    );

    let listener = tokio::net::TcpListener::bind(config.listen_socket_addr())
        .await
        .with_context(|| format!("failed to bind to {}", config.listen_addr))?;

    info!(addr = %config.listen_addr, "proxy listening");

    // Shared atomic counter — no Mutex needed for a simple increment/decrement.
    // Arc lets us clone a reference cheaply into each spawned task.
    let active = Arc::new(AtomicUsize::new(0));

    loop {
        tokio::select! {
            // Branch 1: a new client connection arrived.
            result = listener.accept() => {
                let (client, addr) = result.context("failed to accept connection")?;
                let config = Arc::clone(&config);
                let active = Arc::clone(&active);

                // Increment before spawn so the count is accurate immediately.
                let count = active.fetch_add(1, Ordering::Relaxed) + 1;
                info!(client = %addr, active = count, "[NEW] connection");

                tokio::spawn(async move {
                    if let Err(e) = proxy::handle_connection(client, config).await {
                        error!(client = %addr, error = %e, "connection error");
                    }
                    // fetch_sub returns the value BEFORE subtracting, so subtract 1 for current.
                    let count = active.fetch_sub(1, Ordering::Relaxed) - 1;
                    info!(client = %addr, active = count, "[DONE] connection");
                });
            }

            // Branch 2: CTRL+C received — stop accepting, let existing tasks finish.
            _ = shutdown_signal() => {
                info!("shutdown signal received — stopping");
                break;
            }
        }
    }

    info!("proxy stopped");
    Ok(())
}

Understanding the logs

When you start the proxy:

INFO a_tcp_passthrough: proxy listening addr=127.0.0.1:8080
  • INFO — log level. This is informational. WARN would indicate something unexpected but recoverable, ERROR is a serious problem.
  • a_tcp_passthrough — the module/crate name. Rust's logging system lets you filter by module.
  • proxy listening — the log message.
  • addr=127.0.0.1:8080 — structured key-value field added to the log. The % prefix means "use the Display implementation of this value."

When a client connects:

INFO a_tcp_passthrough: [NEW] connection client=127.0.0.1:54321 upstream=127.0.0.1:9090
INFO a_tcp_passthrough: [CLOSED] connection client=127.0.0.1:54321
  • client=127.0.0.1:54321 — the client's IP and ephemeral port. The OS assigns the ephemeral port automatically when the client makes a connection. That is why it is a high number (above 32768).
  • [NEW] / [CLOSED] — we print these at the start and end of each connection so you can see how long connections live and how many are active at once.

When you send a request:

$ curl http://localhost:8080/
Hello from backend!

curl opens a TCP connection to port 8080. The proxy connects to port 9090 (your backend). The bytes of the HTTP request flow from curl through the proxy to the backend. The backend's response bytes flow back through the proxy to curl. The proxy never sees or cares that those bytes are HTTP.

Limitations of Option A
  • Breaks with HTTPS — TLS bytes are encrypted. The proxy would try to connect to an upstream and forward encrypted bytes. The upstream would see garbage because it does not know about the TLS session that was negotiated between the client and the proxy. You cannot forward TLS traffic to a plain HTTP backend without terminating TLS first.
  • Cannot load balance — there is only one fixed upstream in the config. To load balance, you need to read the HTTP request to at least know when one request ends and the next begins. At the raw TCP level, you can't tell.
  • Cannot add headers — we never look at the bytes, so we cannot inject X-Forwarded-For or any other header. The backend never knows the real client IP.

5. Option B — HTTP/1.1 Load Balancer

B

Files: src/main.rs, src/proxy.rs, src/http.rs, src/balancer.rs

Option B reads and parses the HTTP request headers, rewrites them with injected proxy headers, and distributes requests across multiple backends using round-robin. This is the core of what a real HTTP reverse proxy does.

httparse — parsing raw HTTP bytes

httparse is a zero-copy HTTP parser. You give it a byte slice and it tells you: the method (GET, POST, etc.), the path (/api/users), the HTTP version, and a list of headers (each a name and value). It does this without allocating memory — it just records the offsets into your existing buffer.

We use it in http.rs inside build_forwarded_request:

let mut headers = [httparse::EMPTY_HEADER; MAX_HEADERS];
let mut req = httparse::Request::new(&mut headers);
let status = req.parse(&buf[..len]).context("failed to parse HTTP request")?;
if status.is_partial() {
    bail!("incomplete HTTP headers");
}
let method = req.method.context("missing HTTP method")?.to_string();
let path = req.path.context("missing HTTP path")?.to_string();

After parsing, req.method, req.path, and req.headers contain the parsed values as slices pointing into your original buffer. No copying until you explicitly call .to_string().

Why we strip and re-inject certain headers

When the proxy forwards a request to the backend, it rewrites the headers. Some headers must be stripped from the client's original request and replaced with the proxy's own values:

  • Host — the client sends Host: example.com, but the backend should see Host: 127.0.0.1:9091 (the upstream it is actually talking to). If we forwarded the original Host header, the backend might be confused about who it is serving.
  • X-Forwarded-For — if a malicious client sends X-Forwarded-For: 1.2.3.4, and we blindly forward it, the backend thinks the real client is 1.2.3.4. We strip the client's version and inject our own, which contains the real client IP as seen by the proxy. This is called anti-spoofing.
  • Connection — HTTP keep-alive semantics between client and proxy are separate from keep-alive between proxy and upstream. We always send Connection: close to the upstream to keep things simple.
  • Via — RFC standard for marking that a request passed through a proxy. We inject Via: 1.1 rust-proxy.
  • X-Request-ID — same anti-spoofing reason as X-Forwarded-For. We generate a fresh UUID for every request.

The full build_forwarded_request function

use anyhow::{bail, Context, Result};

const MAX_HEADERS: usize = 64;

/// Parses an HTTP/1.x request header block and rebuilds it for proxy forwarding.
///
/// Injected headers (X-Forwarded-For, X-Request-ID, Via, Connection) are added
/// fresh from our values. Any client-supplied versions of these headers are stripped
/// to prevent spoofing.
///
/// Returns `(rewritten_header_bytes, method, path)`.
pub fn build_forwarded_request(
    buf: &[u8],
    len: usize,
    client_ip: &str,
    upstream_host: &str,
    request_id: &str,
) -> Result<(Vec<u8>, String, String)> {
    let mut headers = [httparse::EMPTY_HEADER; MAX_HEADERS];
    let mut req = httparse::Request::new(&mut headers);

    let status = req.parse(&buf[..len]).context("failed to parse HTTP request")?;
    if status.is_partial() {
        bail!("incomplete HTTP headers");
    }

    let method = req.method.context("missing HTTP method")?.to_string();
    let path = req.path.context("missing HTTP path")?.to_string();

    // Headers we control — strip any client-supplied versions to prevent spoofing
    let strip = ["host", "connection", "x-forwarded-for", "x-request-id", "via"];

    let mut out = Vec::with_capacity(len + 256);

    // 1. Request line (unchanged)
    out.extend_from_slice(method.as_bytes());
    out.push(b' ');
    out.extend_from_slice(path.as_bytes());
    out.extend_from_slice(b" HTTP/1.1\r\n");

    // 2. Rewritten Host
    out.extend_from_slice(b"Host: ");
    out.extend_from_slice(upstream_host.as_bytes());
    out.extend_from_slice(b"\r\n");

    // 3. Original headers minus the ones we control
    for header in req.headers.iter() {
        if header.name.is_empty() {
            break;
        }
        if strip.iter().any(|s| header.name.eq_ignore_ascii_case(s)) {
            continue;
        }
        out.extend_from_slice(header.name.as_bytes());
        out.extend_from_slice(b": ");
        out.extend_from_slice(header.value);
        out.extend_from_slice(b"\r\n");
    }

    // 4. Injected observability + proxy headers
    out.extend_from_slice(b"X-Forwarded-For: ");
    out.extend_from_slice(client_ip.as_bytes());
    out.extend_from_slice(b"\r\n");

    out.extend_from_slice(b"X-Request-ID: ");
    out.extend_from_slice(request_id.as_bytes());
    out.extend_from_slice(b"\r\n");

    out.extend_from_slice(b"Via: 1.1 rust-proxy\r\n");
    out.extend_from_slice(b"Connection: close\r\n");

    // 5. End of headers
    out.extend_from_slice(b"\r\n");

    Ok((out, method, path))
}

Step by step:

  1. Parse the raw bytes with httparse. If parsing fails or is incomplete, we will send a 400 to the client.
  2. Build a new byte buffer for the outgoing request. Start with the request line (method + path + HTTP/1.1).
  3. Write the rewritten Host header pointing at the upstream's address.
  4. Copy all original headers except the ones in the strip list. The eq_ignore_ascii_case comparison handles both X-Forwarded-For and x-forwarded-for — HTTP headers are case-insensitive.
  5. Append the injected headers: X-Forwarded-For with the real client IP, X-Request-ID with a UUID, Via and Connection: close.
  6. Write the final \r\n that signals end of headers.

The round-robin balancer

use std::net::SocketAddr;
use std::sync::atomic::{AtomicUsize, Ordering};

pub struct Balancer {
    upstreams: Vec<SocketAddr>,
    counter: AtomicUsize,
}

impl Balancer {
    pub fn new(upstreams: Vec<SocketAddr>) -> Self {
        Self {
            upstreams,
            counter: AtomicUsize::new(0),
        }
    }

    /// Returns the next upstream address using round-robin selection.
    /// Lock-free: uses AtomicUsize with Relaxed ordering.
    pub fn next(&self) -> SocketAddr {
        let idx = self.counter.fetch_add(1, Ordering::Relaxed) % self.upstreams.len();
        self.upstreams[idx]
    }

    pub fn len(&self) -> usize {
        self.upstreams.len()
    }
}

The logic is beautifully simple. counter is an AtomicUsize — a number that can be read and incremented safely from multiple threads with no lock. fetch_add(1, Ordering::Relaxed) atomically increments the counter and returns the old value. We take old_value % n_upstreams to get an index that cycles through 0, 1, 2, 0, 1, 2, ... endlessly.

Ordering::Relaxed means we don't need any synchronization guarantees beyond the atomic increment itself. We don't care about the order of other memory operations around this. For a counter that is just about "which upstream is next," Relaxed is correct and slightly faster than Acquire/Release.

With 3 upstreams configured (9091, 9092, 9093), requests are distributed: request 1 → 9091, request 2 → 9092, request 3 → 9093, request 4 → 9091, and so on.

Understanding the logs

INFO [a1b2c3d4] GET / → 127.0.0.1:9091 in 2ms
INFO [e5f6a7b8] GET / → 127.0.0.1:9092 in 1ms
  • [a1b2c3d4] — the first 8 characters of the UUID request ID. We only show 8 chars in logs to keep lines short, but the full UUID is forwarded to the backend in X-Request-ID. If you see an error in the backend log for request ID a1b2c3d4..., you can find the corresponding entry in the proxy log instantly.
  • GET / — HTTP method and path extracted from the parsed request.
  • → 127.0.0.1:9091 — which upstream received this request. You can watch the logs and see the round-robin distribution happening in real time.
  • in 2ms — total wall-clock time from when the proxy received the request to when it finished writing the response. This includes parsing, connecting to upstream, and the full response transfer.

What the upstream receives

When you send GET / HTTP/1.1 from curl with a Host: localhost header, here is what actually arrives at the backend:

GET / HTTP/1.1
Host: 127.0.0.1:9091
X-Forwarded-For: 127.0.0.1
X-Request-ID: a1b2c3d4-e5f6-a7b8-c9d0-e1f2a3b4c5d6
Via: 1.1 rust-proxy
Connection: close

The original Host: localhost from the client is gone, replaced with the upstream's actual address. The three injected headers are fresh from the proxy. Connection: close tells the upstream to close the connection after this response — no keep-alive complexity between proxy and backend.

Limitations of Option B
  • No TLS — all traffic is plaintext. Anyone on the network can read requests and responses. The connection between client and proxy is unencrypted.
  • No health checking — dead upstreams still get requests. If backend 9092 crashes, the proxy still sends every third request to it, which returns a 502 to the client. There is no automatic removal of dead backends from rotation.

6. Option C — HTTPS + TLS + Health Checks

C

Files: src/main.rs, src/proxy.rs, src/tls.rs, src/health.rs, src/balancer.rs

Option C adds two major production features: TLS termination (clients connect via HTTPS) and health checks (dead backends are automatically removed from rotation, returning 503 when all are down).

rustls — TLS without OpenSSL

rustls is a TLS implementation written entirely in Rust. Most software uses OpenSSL, which is a giant C library with a history of serious security vulnerabilities (Heartbleed being the most famous). rustls is a modern, memory-safe alternative. It supports TLS 1.2 and TLS 1.3.

TLS 1.2 vs 1.3 — TLS 1.3 is faster (the handshake takes one fewer round trip), more secure (removes older cipher suites with known weaknesses), and simpler. TLS 1.2 is still in use because many old clients and servers don't support 1.3 yet. We support both.

rcgen is a library that generates a self-signed certificate in memory at startup. You do not need to run OpenSSL commands or manage files. This is perfect for development — the cert is generated fresh each time the process starts.

tls.rs — building the TLS acceptor

use anyhow::{Context, Result};
use rustls::pki_types::{CertificateDer, PrivateKeyDer, PrivatePkcs8KeyDer};
use rustls::ServerConfig;
use std::sync::Arc;
use tokio_rustls::TlsAcceptor;

use crate::config::TlsConfig;

pub fn build_acceptor(cfg: &TlsConfig) -> Result<TlsAcceptor> {
    let (certs, key) = if cfg.cert_path.is_empty() {
        generate_self_signed()?
    } else {
        load_pem(&cfg.cert_path, &cfg.key_path)?
    };

    let server_config = ServerConfig::builder_with_provider(Arc::new(
        rustls::crypto::ring::default_provider(),
    ))
    .with_safe_default_protocol_versions()
    .context("failed to set TLS protocol versions")?
    .with_no_client_auth()
    .with_single_cert(certs, key)
    .context("failed to build TLS server config")?;

    Ok(TlsAcceptor::from(Arc::new(server_config)))
}

fn generate_self_signed() -> Result<(Vec<CertificateDer<'static>>, PrivateKeyDer<'static>)> {
    let cert = rcgen::generate_simple_self_signed(vec!["localhost".to_string()])
        .context("failed to generate self-signed cert")?;
    let cert_der = CertificateDer::from(cert.cert.der().to_vec());
    let key_der = PrivateKeyDer::Pkcs8(PrivatePkcs8KeyDer::from(
        cert.key_pair.serialize_der(),
    ));
    Ok((vec![cert_der], key_der))
}

Line by line:

  • ServerConfig::builder_with_provider — start building a TLS server config. ring is the cryptographic backend (provides the actual encryption algorithms).
  • .with_safe_default_protocol_versions() — enable TLS 1.2 and 1.3, disable older insecure versions (TLS 1.0, 1.1, SSL 2/3).
  • .with_no_client_auth() — the server will not require clients to present a certificate. Standard for public HTTPS servers. (Mutual TLS / mTLS would use a different call here.)
  • .with_single_cert(certs, key) — load the certificate and private key. The cert is what the server shows to clients as proof of identity. The key is kept secret and used to sign the handshake.
  • TlsAcceptor::from(Arc::new(server_config)) — wrap the config in an acceptor. The Arc allows it to be cloned cheaply and shared across all connection-handling tasks.

When a client connects, we call acceptor.accept(tcp). This performs the full TLS handshake over the raw TCP stream and returns a TlsStream — a wrapper around the TCP stream that transparently encrypts/decrypts everything you read and write through it.

health.rs — the background health checker

use std::net::SocketAddr;
use std::sync::{
    atomic::{AtomicBool, Ordering},
    Arc,
};
use std::time::Duration;
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpStream;
use tokio::time::timeout;
use tracing::{debug, warn};

pub type HealthFlags = Arc<Vec<AtomicBool>>;

pub fn new_flags(n: usize) -> HealthFlags {
    Arc::new((0..n).map(|_| AtomicBool::new(true)).collect())
}

pub fn spawn_checkers(
    upstreams: Vec<SocketAddr>,
    flags: HealthFlags,
    interval: Duration,
    probe_timeout: Duration,
    path: String,
) {
    for (i, addr) in upstreams.into_iter().enumerate() {
        let flags = Arc::clone(&flags);
        let path = path.clone();
        tokio::spawn(async move {
            loop {
                tokio::time::sleep(interval).await;
                let healthy = probe(addr, probe_timeout, &path).await;
                flags[i].store(healthy, Ordering::Relaxed);
                if healthy {
                    debug!(upstream = %addr, "health check OK");
                } else {
                    warn!(upstream = %addr, "health check FAILED — marking unhealthy");
                }
            }
        });
    }
}

async fn probe(addr: SocketAddr, probe_timeout: Duration, path: &str) -> bool {
    matches!(timeout(probe_timeout, do_probe(addr, path)).await, Ok(true))
}

async fn do_probe(addr: SocketAddr, path: &str) -> bool {
    let Ok(mut stream) = TcpStream::connect(addr).await else {
        return false;
    };
    let req = format!("GET {} HTTP/1.0\r\nHost: {}\r\n\r\n", path, addr);
    if stream.write_all(req.as_bytes()).await.is_err() {
        return false;
    }
    let mut buf = [0u8; 256];
    let n = match stream.read(&mut buf).await {
        Ok(n) if n > 0 => n,
        _ => return false,
    };
    let Ok(s) = std::str::from_utf8(&buf[..n]) else {
        return false;
    };
    s.starts_with("HTTP/")
        && s.split_whitespace()
            .nth(1)
            .map_or(false, |c| c.starts_with('2'))
}

What this code does:

  • HealthFlags is a type alias for Arc<Vec<AtomicBool>> — a shared, reference-counted vector of atomic booleans, one per upstream. true = healthy, false = dead.
  • new_flags(n) creates n flags all initialized to true (start optimistic — assume everyone is up).
  • spawn_checkers starts one background task per upstream. Each task loops forever: sleep for interval seconds, run a probe, update the flag.
  • do_probe makes a real TCP connection and sends GET /health HTTP/1.0. It reads the first 256 bytes of the response. If the response starts with HTTP/ and the status code starts with 2 (meaning 200–299), the backend is healthy.
  • We use HTTP/1.0 (not 1.1) in the probe because HTTP/1.0 does not require a Host header, making the probe simpler. We add Host anyway for compatibility.
  • The entire probe is wrapped in a timeout. If the backend is hung and never responds, we don't wait forever — we fail after probe_timeout seconds.

balancer.rs — health-aware round-robin

use std::net::SocketAddr;
use std::sync::atomic::{AtomicUsize, Ordering};

use crate::health::HealthFlags;

pub struct Balancer {
    upstreams: Vec<SocketAddr>,
    health: HealthFlags,
    counter: AtomicUsize,
}

impl Balancer {
    pub fn new(upstreams: Vec<SocketAddr>, health: HealthFlags) -> Self {
        Self {
            upstreams,
            health,
            counter: AtomicUsize::new(0),
        }
    }

    /// Returns the next healthy upstream using round-robin selection.
    /// Returns None if all upstreams are unhealthy.
    pub fn next_healthy(&self) -> Option<SocketAddr> {
        let start = self.counter.fetch_add(1, Ordering::Relaxed);
        let n = self.upstreams.len();
        for i in 0..n {
            let idx = (start + i) % n;
            if self.health[idx].load(Ordering::Relaxed) {
                return Some(self.upstreams[idx]);
            }
        }
        None
    }

    pub fn len(&self) -> usize {
        self.upstreams.len()
    }
}

The key change from Option B: next_healthy() instead of next(). We still advance the counter (to maintain fair distribution), but then we linear-scan from that position, wrapping around, looking for the first upstream whose health flag is true. If all flags are false, we return None.

When next_healthy() returns None, the proxy responds with 503 Service Unavailable — a proper HTTP error response rather than a TCP reset. The client gets a meaningful error message instead of a broken connection.

The beauty of AtomicBool here: the health checker task and the request-handling tasks are running concurrently on different threads. When the health checker calls flags[i].store(false, Ordering::Relaxed), the change is visible to all other threads instantly (atomics are by definition visible across threads). No mutex, no lock contention.

Understanding the startup logs

INFO c_tls_health_checks: HTTPS proxy listening addr=0.0.0.0:8444 upstreams=2
WARN c_tls_health_checks: upstream=127.0.0.1:9092 "health check FAILED — marking unhealthy"

Why 0.0.0.0 instead of 127.0.0.1?

127.0.0.1 is the loopback interface — only connections from the same machine can reach it. 0.0.0.0 means "listen on all network interfaces" — connections from other machines on the network can reach it too. In a development environment, 127.0.0.1 is safer. In a production server, you often want 0.0.0.0 so the server is reachable from the network.

Why is the health check FAILED warning expected?

The health checker starts immediately and begins probing all upstreams. If some backends are not running (perhaps you only started one of the two for testing), the probe correctly reports them as unhealthy. This is not a bug — this is the system working as designed. Once you start the backend, the next probe will succeed and the flag will flip back to true.

Testing with curl

$ curl -k https://localhost:8444/
Hello from backend!

The -k flag tells curl "skip certificate verification." Without it, curl would refuse to connect because our self-signed certificate is not signed by a trusted authority that curl's certificate store knows about. The -k flag is only appropriate for development and testing — never use it in production scripts that talk to real servers.

Limitations of Option C
  • HTTP/1.1 only — we still parse HTTP ourselves and use raw byte copying. Each client connection can only have one in-flight request at a time. High-traffic clients that support HTTP/2 can't benefit from multiplexing.

7. Option D — HTTP/2 via hyper + ALPN

D

Files: src/main.rs, src/proxy.rs, src/tls.rs

Option D replaces the hand-written HTTP parser with hyper, Rust's most widely-used HTTP library. By doing this, we get HTTP/2 multiplexing for free (hyper handles the framing), and we get typed request/response objects instead of raw bytes. The proxy now accepts both HTTP/1.1 and HTTP/2 clients, negotiated automatically during the TLS handshake via ALPN.

hyper — typed HTTP instead of raw bytes

In Options B and C, we managed HTTP as bytes ourselves: read into a buffer, parse with httparse, write rewritten bytes back out. This is educational, but tedious. hyper gives you typed objects:

  • Request<Incoming> — an HTTP request where the body is a streaming Incoming type that can be read incrementally.
  • Response<BoxBody> — an HTTP response with a boxed body type that abstracts over both empty error responses and streaming upstream responses.
  • StatusCode::SERVICE_UNAVAILABLE instead of the hardcoded bytes b"HTTP/1.1 503...".
  • URI parsing, header access, method types — all provided as safe, well-tested abstractions.

ALPN — negotiating HTTP version during the TLS handshake

In Option D's tls.rs, we add one important line to the TLS configuration:

// Advertise HTTP/2 and HTTP/1.1 during TLS handshake (ALPN)
server_config.alpn_protocols = vec![b"h2".to_vec(), b"http/1.1".to_vec()];

This tells the TLS layer to include these protocol names in the TLS handshake's ServerHello message. When a client connects and sends its ClientHello with its own list of protocols, rustls picks the best match (preferring h2 since it is listed first) and includes it in the handshake response.

By the time the TLS handshake completes, both sides know which protocol was agreed on. We read that negotiated protocol like this:

let alpn = tls_stream.get_ref().1.alpn_protocol().map(|p| p.to_vec());

get_ref().1 accesses the TLS session state inside the stream. alpn_protocol() returns the agreed-upon protocol as bytes — either b"h2" or b"http/1.1" or None if no ALPN was negotiated. We use this to decide which HTTP version handler to use.

Dispatching based on ALPN

if alpn.as_deref() == Some(b"h2") {
    if let Err(e) = server_http2::Builder::new(TokioExecutor::new())
        .serve_connection(TokioIo::new(tls_stream), service)
        .await
    {
        warn!(error = %e, "http2 connection error");
    }
} else {
    if let Err(e) = server_http1::Builder::new()
        .serve_connection(TokioIo::new(tls_stream), service)
        .await
    {
        warn!(error = %e, "http1 connection error");
    }
}

If ALPN negotiated h2, we hand the connection to http2::Builder. It handles all the HTTP/2 framing, stream multiplexing, header compression (HPACK), and flow control. For each incoming HTTP/2 request (potentially many simultaneously on the same connection), it calls our service once.

If ALPN negotiated http/1.1 (or nothing), we use http1::Builder. Same service, different HTTP version handling.

The service object is the same in both cases — it does not need to know which HTTP version it is serving. This is the point of the abstraction.

The Service trait

In Rust, a trait is like an interface in Java or Go. It defines a set of methods a type must implement. hyper's Service trait defines how a type handles incoming requests:

#[derive(Clone)]
pub struct ProxyService {
    pub balancer: Arc<Balancer>,
    pub config: Arc<Config>,
    pub client_ip: String,
}

impl Service<Request<Incoming>> for ProxyService {
    type Response = Response<BoxBody>;
    type Error = Infallible;
    type Future = Pin<Box<dyn Future<Output = Result<Self::Response, Self::Error>> + Send>>;

    fn call(&self, req: Request<Incoming>) -> Self::Future {
        let this = self.clone();
        Box::pin(async move { Ok(this.handle(req).await) })
    }
}

Breaking down the types:

  • type Response = Response<BoxBody> — when we handle a request, we return a typed HTTP response.
  • type Error = Infallible — Infallible is a type that cannot exist. It means this service never returns an error from call(). Instead of propagating errors, we catch them inside handle() and return 502/503 responses. The client always gets an HTTP response, never a broken connection.
  • type Future = Pin<Box<dyn Future<...>>> — the return type of call() is a boxed, pinned future. This is the standard way to return an async value from a trait method in Rust. The Pin ensures the future does not move in memory while awaited.
  • self.clone() — we clone the service to move into the async block. This is cheap because everything inside is wrapped in Arc (reference-counted pointers — cloning an Arc just increments a counter).

BoxBody — a unified body type

In HTTP/2, bodies are streams of bytes. For error responses (502, 503), we want an empty body. For proxied responses, we want to stream the upstream's response body back to the client.

BoxBody is a type alias for a boxed body that can hold either:

pub type BoxBody = http_body_util::combinators::BoxBody<Bytes, hyper::Error>;

fn empty_body() -> BoxBody {
    Empty::<Bytes>::new()
        .map_err(|_: Infallible| unreachable!())
        .boxed()
}

fn error_response(status: StatusCode) -> Response<BoxBody> {
    Response::builder()
        .status(status)
        .header("content-length", "0")
        .header("connection", "close")
        .body(empty_body())
        .unwrap()
}

For the proxied response, we take the upstream's Incoming body and box it:

response.map(|body| body.boxed())

This streams bytes from upstream directly to the client without buffering the entire body in memory — important for large file downloads.

Forwarding to backends over HTTP/1.1

// HTTP/1.1 handshake with upstream
let (mut sender, conn) = match http1::Builder::new()
    .handshake(TokioIo::new(stream))
    .await
{
    Ok(v) => v,
    Err(e) => { return error_response(StatusCode::BAD_GATEWAY); }
};
tokio::spawn(conn);

// Forward request
let response = match sender.send_request(forwarded).await {
    Ok(r) => r,
    Err(e) => { return error_response(StatusCode::BAD_GATEWAY); }
};

Even though clients can connect via HTTP/2, we forward to backends over HTTP/1.1. Why? Backends are simple application servers. They don't benefit from HTTP/2 over an internal loopback connection. HTTP/2 benefits are about multiplexing over high-latency connections (the internet). On a local network, HTTP/1.1 is simpler and works fine.

http1::Builder::new().handshake(stream) initializes an HTTP/1.1 client connection to the upstream and returns two things:

  • sender — a handle to send requests.
  • conn — a Future that drives the connection state machine (reads responses, handles keep-alive, etc).

We tokio::spawn(conn) to run the connection driver concurrently in the background, then use sender.send_request(forwarded) to send our request and wait for the response.

URI rewriting

When a client sends a request to the proxy, the URI in the request line is typically path-only: GET /api/users HTTP/1.1. But in some cases (particularly HTTP proxies in browsers), the client might send an absolute URI: GET http://proxy.example.com/api/users HTTP/1.1.

The backend should receive a path-only URI. We rewrite it:

// Rewrite URI to path-only (backend expects GET /path HTTP/1.1, not absolute URI)
let path_and_query = parts.uri
    .path_and_query()
    .map(|p| p.as_str())
    .unwrap_or("/");
parts.uri = path_and_query.parse()?;

So whether the client sent /hello or https://myproxy.com/hello?q=1, the backend always receives /hello?q=1.

The complete handle() method

impl ProxyService {
    async fn handle(&self, req: Request<Incoming>) -> Response<BoxBody> {
        let start = Instant::now();
        let request_id = Uuid::new_v4().to_string();
        let method = req.method().clone();
        let path = req.uri().path().to_string();

        // Pick healthy upstream
        let upstream_addr = match self.balancer.next_healthy() {
            Some(addr) => addr,
            None => {
                warn!(request_id = %&request_id[..8], "all upstreams unhealthy — sent 503");
                return error_response(StatusCode::SERVICE_UNAVAILABLE);
            }
        };

        // Build the forwarded request
        let forwarded = match build_forwarded_request(req, upstream_addr, &self.client_ip, &request_id) {
            Ok(r) => r,
            Err(e) => {
                warn!(request_id = %&request_id[..8], error = %e, "failed to build forwarded request — sent 502");
                return error_response(StatusCode::BAD_GATEWAY);
            }
        };

        // Connect to upstream
        let connect_dur = Duration::from_secs(self.config.timeouts.connect_timeout_secs);
        let stream = match timeout(connect_dur, TcpStream::connect(upstream_addr)).await {
            Ok(Ok(s)) => s,
            Ok(Err(e)) => {
                warn!(request_id = %&request_id[..8], upstream = %upstream_addr, error = %e, "upstream unreachable — sent 502");
                return error_response(StatusCode::BAD_GATEWAY);
            }
            Err(_) => {
                warn!(request_id = %&request_id[..8], upstream = %upstream_addr, "upstream connect timeout — sent 502");
                return error_response(StatusCode::BAD_GATEWAY);
            }
        };

        // HTTP/1.1 handshake with upstream
        let (mut sender, conn) = match http1::Builder::new()
            .handshake(TokioIo::new(stream))
            .await
        {
            Ok(v) => v,
            Err(e) => {
                warn!(request_id = %&request_id[..8], error = %e, "http1 handshake failed — sent 502");
                return error_response(StatusCode::BAD_GATEWAY);
            }
        };
        tokio::spawn(conn);

        // Forward request
        let response = match sender.send_request(forwarded).await {
            Ok(r) => r,
            Err(e) => {
                warn!(request_id = %&request_id[..8], error = %e, "upstream request failed — sent 502");
                return error_response(StatusCode::BAD_GATEWAY);
            }
        };

        let elapsed = start.elapsed().as_millis();
        info!(
            "[{}] {} {} → {} in {}ms",
            &request_id[..8], method, path, upstream_addr, elapsed
        );

        // Stream the upstream response body back to the client
        response.map(|body| body.boxed())
    }
}

8. Concepts Glossary

Quick reference for every technical term used in this guide.

TCP

Transmission Control Protocol. A reliable, ordered, bidirectional byte stream between two programs over a network. TCP guarantees that bytes arrive in the same order they were sent, with no gaps. TCP does not know about HTTP, JSON, or any higher-level concept — it just moves bytes. Port numbers let multiple programs on the same machine each have their own TCP connections.

HTTP

HyperText Transfer Protocol. A text-based request/response protocol that runs over TCP. A request has a method (GET, POST, etc.), a path (/api/users), headers (key-value metadata), and an optional body. A response has a status code (200, 404, 502, etc.), headers, and an optional body. HTTP/1.1 allows one request per connection at a time. The protocol is fully human-readable text, which makes debugging straightforward.

HTTPS

HTTP over TLS. The HTTP request/response format is the same, but the bytes are encrypted before going on the network. To an observer, HTTPS traffic looks like random bytes. The correct decryption key is only known by the client and server. HTTPS protects against eavesdropping and tampering. The HTTPS port is conventionally 443.

TLS

Transport Layer Security. An encryption protocol that wraps a TCP connection. TLS authenticates the server (proves you are talking to the right machine via certificates), negotiates shared encryption keys using public-key cryptography, and encrypts all further communication. TLS 1.3 is the current version. The handshake takes one or two network round trips before application data can flow.

ALPN

Application-Layer Protocol Negotiation. A TLS extension that allows the client and server to agree on which application protocol to use (HTTP/1.1 vs HTTP/2) as part of the TLS handshake, at no extra cost in round trips. The client sends a list: ["h2", "http/1.1"]. The server picks the best one it supports and includes it in the handshake response. After the handshake completes, both sides know which protocol to speak.

async/await

A language feature for writing concurrent code that looks sequential. An async fn returns a Future instead of running immediately. Calling .await on a Future suspends the current function until the Future completes, but does not block the thread — other tasks can run in the meantime. This lets you write code like "connect to server, then send request, then read response" in a natural linear style, while the runtime handles interleaving with thousands of other concurrent operations.

Future

A value representing a computation that has not finished yet. In Rust, a Future is a state machine generated by the compiler from an async fn. It stores all the local variables and the "current position" of the function. When polled by the runtime, it either makes progress and suspends (returning Pending) or finishes (returning Ready). Futures do nothing unless polled — they are lazy. The Tokio runtime is what polls them.

Tokio

An async runtime for Rust. It provides a thread pool, an event loop backed by epoll/kqueue/IOCP, timers, async TCP/UDP sockets, channels, and utilities for spawning and scheduling tasks. When you write #[tokio::main], Tokio starts a thread pool and begins running your async main function. Without a runtime, async code in Rust does nothing.

tokio::spawn

Creates a new Tokio task. A task is a lightweight unit of work — like a thread, but scheduled by Tokio rather than the OS. You can have millions of tasks on a handful of threads. Each spawned task runs concurrently with all other tasks. tokio::spawn takes an async block, creates a task for it, and immediately returns a JoinHandle that you can await if you want to wait for the task to finish.

AtomicBool / AtomicUsize

Atomic types that can be read and written from multiple threads simultaneously without locks. The CPU provides hardware instructions that guarantee atomicity — an increment or store operation appears to happen instantaneously to all other threads. AtomicBool is used for the health flags (healthy/unhealthy per upstream). AtomicUsize is used for the round-robin counter and active connection count. Atomics are the right tool for simple shared counters and flags where you don't need to coordinate complex state.

UUID

Universally Unique Identifier. A 128-bit number formatted as 32 hexadecimal digits with hyphens: a1b2c3d4-e5f6-a7b8-c9d0-e1f2a3b4c5d6. Generated randomly (UUID v4). The probability of two UUIDs colliding is astronomically low. We generate one per request and use the first 8 characters in logs and the full UUID in the X-Request-ID header. This lets you search for a specific request across any log in the system.

Round-robin

A load balancing algorithm that cycles through a list in order: upstream 1, then 2, then 3, then back to 1. Simple, fair, and stateless — each upstream gets roughly the same number of requests. It does not account for differences in upstream capacity or current load. Alternatives include least-connections (send to the upstream with the fewest active requests), random, and weighted round-robin.

Health check

A periodic test to verify that an upstream is alive and able to serve requests. Typically: make a TCP connection, send a minimal HTTP request (GET /health HTTP/1.0), check that the response has a 2xx status code. If the check fails, the upstream is marked unhealthy and removed from the load balancing rotation. The check runs again on a timer — when the upstream recovers, it is automatically re-added to rotation.

502 Bad Gateway

An HTTP status code meaning "the proxy received an invalid or no response from the upstream." You get a 502 when the upstream is running but misbehaving (returning garbage), or when the proxy can connect to the upstream port but the connection immediately fails. In our proxy, we return 502 when TcpStream::connect fails or when the upstream connection times out during an active request.

503 Service Unavailable

An HTTP status code meaning "the server cannot handle the request right now, usually temporarily." In our proxy, we return 503 specifically when the health check has marked all upstreams as unhealthy and there is nobody to forward the request to. This is the correct response because the situation is temporary — once backends recover and pass health checks, the 503s stop.

HPACK compression

The header compression algorithm used in HTTP/2. In HTTP/1.1, every request sends all headers as plaintext text, even the ones that never change (like Accept-Encoding, User-Agent). HPACK maintains a shared "header table" on both sides of the connection. Once a header has been sent, future requests can refer to it by index instead of sending it again. This significantly reduces the overhead of many small requests to the same server.

Multiplexing

Sending multiple logical streams of data over a single physical connection, interleaved. HTTP/2 multiplexing allows many requests to be in flight simultaneously on one TCP connection, with responses coming back in any order. Each request/response pair is a "stream" identified by a number. The HTTP/2 framing layer handles splitting requests into frames, labeling them with stream IDs, and reassembling them. Without multiplexing (HTTP/1.1), you need one TCP connection per in-flight request, which is expensive.
