Tokio & Async Rust

From raw Futures to TCP proxies — understand the low-level network programming layer before building on it.

This guide covers five topics in order: what a Future is, why Pin exists, how Tokio's runtime schedules tasks, how async I/O avoids blocking threads, and how tokio::io::copy powers your TCP proxy. Each section has runnable code examples.

1. Why Study Tokio Before Building a Proxy

A reverse proxy spends almost all of its time doing two things: waiting for bytes to arrive and forwarding bytes to the next hop. If you use one OS thread per connection, you burn megabytes of stack memory per connection. At 10,000 connections, that is tens of gigabytes just for stacks — and most of those threads are idle, waiting on the network.

Tokio solves this with async I/O. Instead of one thread per connection, you get one task per connection — a tiny state machine that costs a few hundred bytes. A handful of OS threads can drive hundreds of thousands of tasks. Understanding how this works at the poll() level is what makes the proxy code readable, not magical.

The goal By the end of this guide, when you see tokio::io::copy(&mut client, &mut upstream).await in the proxy, you should be able to explain exactly what happens — from the .await keyword down to the OS event loop.

2. Futures & Polling

What is a Future?

A Future is a value that represents a computation that hasn't completed yet. In Rust, it is a trait with a single method:

trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

enum Poll<T> {
    Ready(T),   // done, here's the value
    Pending,    // not done yet, call me later
}

That is the entire interface. There are no callbacks, no event emitters, no promises with .then() chains. A Future is a thing you call poll() on, and it either gives you a value or says "not yet."

How .await works

When you write let x = some_future.await;, the compiler generates code that does roughly this:

loop {
    match some_future.poll(cx) {
        Poll::Ready(value) => break value,
        Poll::Pending => {
            // yield control back to the runtime
            // runtime will call poll() again when waker fires
            return Poll::Pending;
        }
    }
}

The crucial detail: the current function also returns Pending. This is how suspension propagates up the call stack. Each .await is a potential suspension point where the runtime can park this task and go run something else.

The Waker

The cx parameter contains a Waker — a handle that the future uses to tell the runtime "I'm ready to be polled again." Without calling the waker, the runtime has no reason to poll the future again, and it will sit there forever.

For I/O futures (like reading from a socket), the waker is hooked up to the OS event system. When bytes arrive on the socket, the OS notifies Tokio, Tokio calls the waker, and the waker re-schedules the task for polling. No busy-waiting, no spin loops, no wasted CPU.

    Your code              Tokio runtime             OS (epoll/IOCP)
    ─────────              ─────────────             ───────────────
    stream.read().await
         │
         ▼
    poll() → Pending       registers waker           socket registered
         │                      │
         ▼                      │
    (task parked)               │
                                │                    data arrives!
                                │◄────────────────── epoll_wait returns
                                │
                           waker.wake()
                                │
                                ▼
                           re-polls task
                                │
                                ▼
                        poll() → Ready(bytes)
                                │
                                ▼
                        task continues

Building a custom Future

To make this concrete, here is a complete Future that counts down from N to 0:

struct Countdown {
    remaining: u32,
}

impl Future for Countdown {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.remaining == 0 {
            Poll::Ready("done!")
        } else {
            println!("remaining: {}", self.remaining);
            self.remaining -= 1;
            cx.waker().wake_by_ref();  // tell runtime to poll us again
            Poll::Pending
        }
    }
}

When you .await this, Tokio calls poll() four times (for a countdown from 3): three times it returns Pending and decrements, and the fourth time it returns Ready("done!"). Each time it returns Pending, it calls wake_by_ref() to ensure the runtime polls it again immediately.

What happens without wake()? If you return Poll::Pending without calling the waker, the runtime assumes the future is waiting for some external event. It will never poll again. Your future is stuck forever. This is the most common bug when implementing custom futures.

3. Pin & the Self-Referential Struct Problem

This section explains the tweet from Debasish Ghosh: "A &mut borrow alive at .await would require storing a pointer into the future itself — self-referential struct — unsound if moved."

What async fn compiles to

An async fn is syntactic sugar. The compiler transforms it into a state machine — an enum where each variant holds the local variables alive at that suspension point.

// What you write:
async fn example(data: &mut Vec<u8>) {
    let slice = &data[..];          // borrows data
    tokio::time::sleep(...).await;   // suspension point!
    println!("{:?}", slice);         // uses borrow after .await
}

// What the compiler generates (simplified):
enum ExampleFuture<'a> {
    State0 { data: &'a mut Vec<u8> },
    State1 { data: &'a mut Vec<u8>, slice: &'a [u8] },
    //                               ^^^^^^^^^^^^^^^^
    //        slice points into data — SELF-REFERENTIAL!
    Done,
}

In State1, slice is a reference to the contents of data. Both are fields of the same struct. That makes the struct self-referential — it contains a pointer to its own memory.

Why moving breaks self-referential structs

Before move:                          After move:
┌──────────────────────┐              ┌──────────────────────┐
│ addr: 0x1000         │              │ addr: 0x2000         │
│ data: "hello"        │              │ data: "hello"        │
│ slice: ptr → 0x1000  │──────╮       │ slice: ptr → 0x1000  │──╮
└──────────────────────┘      │       └──────────────────────┘  │
                              │                                  │
                              ▼                                  ▼
                         data (valid)                       0x1000 (FREED!)
                                                            dangling pointer!

When the struct moves from address 0x1000 to 0x2000, the data field moves with it. But slice still points at 0x1000 — the old address. That memory may now be freed or reused. Dereferencing slice is undefined behavior.

How Pin solves this

Pin<&mut T> is a wrapper around a mutable reference that removes the ability to move T. Once a value is pinned, you can never get a plain &mut T to it (unless T: Unpin), which means you can never call std::mem::swap or std::mem::replace on it. The value stays put. Self-references remain valid.

This is why Future::poll takes Pin<&mut Self> instead of &mut self. It guarantees that between polls, the future doesn't move. The compiler-generated self-referential state machine is safe.

Type Unpin? Pin effect
u32, String, Vec Yes (implements Unpin) Pin is a no-op. You can still get &mut freely.
Most async blocks / async fn futures No (!Unpin) Pin prevents &mut access. Cannot be moved. Self-references are safe.

How to pin values in practice

// Heap-pinned (common with spawn, trait objects):
let future = Box::pin(async { ... });
// Type: Pin<Box<dyn Future<Output = T>>>

// Stack-pinned (common inside async fn):
tokio::pin!(future);
// Type: Pin<&mut impl Future<Output = T>>

// tokio::spawn handles pinning internally — you rarely need to think about it:
tokio::spawn(async move { ... });  // future is pinned inside the task
The one-sentence summary Pin exists because async functions compile to self-referential structs, and self-referential structs break if moved. Pin prevents the move.

4. Tokio Runtime & Task Spawning

What the runtime does

When you write #[tokio::main], it creates a multi-threaded runtime with a work-stealing scheduler. Here is what that means:

  1. Thread pool — Tokio starts N worker threads (default: one per CPU core). Each thread has a local task queue.
  2. Task scheduling — When you call tokio::spawn(), the future is wrapped in a task and placed on a worker's queue. When a task yields (hits .await and returns Pending), the worker picks up the next task from its queue.
  3. Work stealing — If a worker's queue is empty, it steals tasks from another worker's queue. This keeps all cores busy without manual load balancing.
  4. I/O driver — A separate component registers sockets with the OS event system. When data arrives, the driver wakes the corresponding task.
                     Tokio Runtime
    ┌──────────────────────────────────────────┐
    │                                          │
    │   Worker Thread 1    Worker Thread 2     │
    │   ┌────────────┐     ┌────────────┐      │
    │   │ Task A      │     │ Task C      │     │
    │   │ Task B      │     │ (idle)      │◄──steal──┐
    │   └────────────┘     └────────────┘      │     │
    │         │                   │             │     │
    │         └───────┬───────────┘             │     │
    │                 │                        │     │
    │           I/O Driver                     │     │
    │           (epoll / IOCP)                 │     │
    │                 │                        │     │
    └─────────────────│────────────────────────┘     │
                      │                              │
                  OS kernel ── socket ready ──► wake task

spawn() requires 'static + Send

When you call tokio::spawn(future), two constraints apply:

  • 'static — The future must own all its data. It cannot borrow from the current scope, because the spawned task may outlive the scope that created it. Fix: use move closures and .clone() where needed.
  • Send — The future must be safe to send between threads, because the work-stealing scheduler may move it from one thread to another. This rules out Rc (use Arc), Cell/RefCell (use Mutex), and raw pointers.
// This compiles — String is 'static + Send, and `move` transfers ownership:
let name = String::from("proxy-task");
tokio::spawn(async move {
    println!("running: {name}");
});

// This does NOT compile — borrows `name`, not 'static:
// tokio::spawn(async {
//     println!("running: {name}");  // ERROR: name is borrowed, not moved
// });

// This does NOT compile — Rc is not Send:
// let rc = std::rc::Rc::new(42);
// tokio::spawn(async move {
//     println!("{rc}");  // ERROR: Rc<i32> cannot be sent between threads
// });

Sequential vs. concurrent execution

// Sequential: 200ms + 200ms = ~400ms total
let a = do_work("A", 200).await;
let b = do_work("B", 200).await;

// Concurrent with spawn: max(200ms, 200ms) = ~200ms total
let handle_a = tokio::spawn(do_work("A", 200));
let handle_b = tokio::spawn(do_work("B", 200));
let a = handle_a.await.unwrap();
let b = handle_b.await.unwrap();

// Concurrent with join! (no spawn, same task, still concurrent):
let (a, b) = tokio::join!(
    do_work("A", 200),
    do_work("B", 200),
);
spawn vs. join! tokio::spawn creates a new task that runs independently on any thread. tokio::join! runs multiple futures concurrently within the same task. Use spawn when you want true parallelism across cores; use join! when you just want to overlap I/O waits.

JoinHandle & error handling

A spawned task returns a JoinHandle<T>. Awaiting it gives you Result<T, JoinError>. If the task panics, the panic is caught and returned as JoinError — it does not crash the runtime. This is different from std threads, where a panic in one thread can sometimes propagate.

let handle = tokio::spawn(async { 42 });
match handle.await {
    Ok(value) => println!("got {value}"),
    Err(e) => println!("task panicked: {e}"),
}

// Abort a long-running task:
handle.abort();

5. Async I/O — TcpListener & Non-Blocking Sockets

What happens when you call TcpListener::bind().await

Under the hood, Tokio does four things:

  1. Creates a socket — calls the OS to allocate a new TCP socket.
  2. Sets it non-blocking — tells the OS to return immediately if no data is available, instead of blocking the thread.
  3. Binds to the address — associates the socket with a local IP and port.
  4. Registers with the I/O driver — Tokio registers the socket with the OS event system (IOCP on Windows, epoll on Linux). The driver will notify Tokio when the socket has events (new connections, data ready, etc.).

The accept loop

let listener = TcpListener::bind("127.0.0.1:3456").await?;

loop {
    // .await here SUSPENDS this task — the thread is free to do other work.
    // When a client connects, IOCP/epoll fires, the waker runs, and
    // this task resumes with the new socket.
    let (socket, addr) = listener.accept().await?;

    // Spawn a task per connection — costs ~200 bytes, not megabytes.
    tokio::spawn(async move {
        handle_connection(socket, addr).await;
    });
}

The key insight: listener.accept().await does not block a thread. The task suspends, the thread picks up another task, and the OS wakes this task when a connection arrives. One thread can serve thousands of listening sockets.

AsyncRead and AsyncWrite

AsyncRead and AsyncWrite are the async equivalents of std::io::Read and std::io::Write. They work the same way — but instead of blocking the thread when no data is available, they return Poll::Pending and let the runtime do other work.

use tokio::io::{AsyncReadExt, AsyncWriteExt};

// Read bytes from a socket (suspends if no data yet):
let n = socket.read(&mut buf).await?;

// Write bytes to a socket (suspends if write buffer is full):
socket.write_all(response.as_bytes()).await?;

// Shut down the write half — signals EOF to the peer:
socket.shutdown().await?;
read() returns 0 = EOF When read() returns Ok(0), the peer has closed their side of the connection. You must check for this! If you keep reading after EOF, you get an infinite loop of zero-byte reads. This is a common bug in network code.

6. tokio::io::copy — The Heart of Your Proxy

What copy() does internally

tokio::io::copy(&mut reader, &mut writer) is a loop that reads from one async stream and writes to another:

// Simplified implementation of tokio::io::copy:
async fn copy(reader: &mut R, writer: &mut W) -> io::Result<u64> {
    let mut buf = [0u8; 8192];
    let mut total = 0u64;
    loop {
        let n = reader.read(&mut buf).await?;  // suspend until data
        if n == 0 { break; }                    // EOF — peer closed
        writer.write_all(&buf[..n]).await?;     // suspend until written
        total += n as u64;
    }
    Ok(total)
}

Each .await is a suspension point. While waiting for data from the reader, the thread is free to handle other tasks. When data arrives, the task wakes up, reads it into the buffer, writes it to the writer, and loops.

Bidirectional copy for a TCP proxy

A TCP proxy needs data flowing in both directions: client-to-upstream and upstream-to-client, simultaneously. You achieve this by splitting each stream and copying in both directions concurrently:

let (mut client_read, mut client_write) = client.into_split();
let (mut upstream_read, mut upstream_write) = upstream.into_split();

// Run both copies at the same time:
tokio::join!(
    io::copy(&mut client_read, &mut upstream_write),    // client → upstream
    io::copy(&mut upstream_read, &mut client_write),    // upstream → client
);

Or use the convenience function:

// Does the same thing in one call:
let (client_to_upstream, upstream_to_client) =
    io::copy_bidirectional(&mut client, &mut upstream).await?;

This IS your TCP proxy

    │──── TCP connect ─────►│                         │
    │                       │──── TCP connect ────────►│
    │                       │                         │
    │──── bytes ───────────►│──── bytes ──────────────►│

Everything connects The proxy calls listener.accept().await (Section 5) to get a client socket. It calls TcpStream::connect().await to reach upstream. Then it calls io::copy (this section) in both directions. Each .await suspends the task (Section 2), Pin keeps the future safe (Section 3), and the runtime (Section 4) multiplexes thousands of these proxy sessions on a few threads.

7. Connecting the Dots

Here is how every concept maps to the proxy code:

Concept Where in the proxy Why it matters
Future::poll() Every .await call Each await is a suspension point — the task yields so others can run
Pin Inside tokio::spawn The future's state machine has self-references; Pin keeps them valid
Waker I/O driver → socket ready OS tells Tokio "data arrived," Tokio wakes the task to resume polling
tokio::spawn One task per connection Thousands of connections on a few threads, not thousands of threads
'static + Send The async move { ... } block Spawned task owns its data and may run on any thread
TcpListener::accept The main accept loop Non-blocking wait for new connections
io::copy The bidirectional data transfer Shuffles bytes between client and upstream without buffering everything
